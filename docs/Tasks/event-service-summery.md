На основе архитектурных схем (

Container.puml
) и задания в проекте (

Project_template.md
), Events Service в экосистеме КиноБездны выполняет несколько важных ролей — как на текущем этапе перехода, так и в целевой архитектуре (To-Be).

Вот зачем он нужен:

1. На текущем этапе (MVP для проверки гипотезы)
Команде нужно было понять, насколько легко и надежно интегрировать Apache Kafka в текущую архитектуру для перехода к событийно-ориентированной модели (Event-Driven Architecture). Поэтому events-service был реализован как MVP (минимально жизнеспособный продукт):

Он предоставляет простое REST API (/api/events/movie, /api/events/user), через которое можно закинуть системное событие.
Он сам выступает как Producer (отправляет это событие в топики Kafka).
И сам же является Consumer'ом (вычитывает из Kafka свои же сообщения и пишет их в лог).
Это позволило разработчикам обкатать инфраструктуру (Kafka + Zookeeper) и посмотреть, как работает публикация и подписка (Publish/Subscribe) без риска сломать основной функционал кинотеатра.

2. В целевой архитектуре (To-Be)
Когда распил монолита будет завершен (паттерн Strangler Fig), Events Service станет полноценным центральным микросервисом для фиксации и хранения истории платформы.

Его зона ответственности в будущем:

Единый журнал событий (Event Log): Будет изолированно вычитывать из Kafka абсолютно все бизнес-события: от «пользователь зарегистрировался» и «прошла транзакция» до «пользователь начал просмотр фильма».
Своя база данных: У него будет выделенная БД (db_events на PostgreSQL), где будут аккумулироваться факты о том, что произошло в системе.
Развязка (Decoupling) доменов: Благодаря Events-сервису, например, сервису платежей (Payments Service) не нужно будет по API напрямую дергать модуль лояльности или оповещений. Платежный сервис просто «кидает» в Kafka событие «Платёж успешен», а Events Service сохраняет это для истории аналитики, в то время как другие заинтересованные сервисы реагируют на него по-своему.
Вкратце: сейчас это песочница, доказывающая, что Kafka в проекте работает стабильно. В будущем — это фундамент для аналитики, биллинга и асинхронного взаимодействия микросервисов КиноБездны.
